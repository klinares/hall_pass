# Decisions

Small, reversible choices made by the team, one line each with the reason. Anything bigger goes in `QUESTIONS.md`.

- 2026-11-19 (phase 0, lead): **UI system is uGUI with TextMeshPro; UI Toolkit is not used.** The scrapbook look needs rotated sprite stickers, hard offset shadows, per-element squash-and-spring tweens, and particles and world-space sprites (dog, crowd) layered with the UI. Those are ordinary RectTransform, Image and Canvas sorting work in uGUI and fight UI Toolkit. uGUI is already in the project, so no package is added.
- 2026-11-19 (phase 0, lead): **Editor is 6000.3.29f1** (the project's own version, at D:\Unity\Editors). The newer 6000.6.10f1 also installed on this machine is not used, and the project is not upgraded.
- 2026-11-19 (phase 0, builder): **Packages stripped for a small web download; Pipeline added.** Added `com.unity.pipeline` 1.0.0 (registry latest, min Unity 6000.0; pulls nuget.mono-cecil and nuget.newtonsoft-json) for Editor control. Removed packages visualscripting, multiplayer.center, collab-proxy, 2d.aseprite, 2d.psdimporter and modules cloth, terrainphysics, vehicles, vr, xr, wind, ai, umbra, androidjni, unityanalytics, video. Kept modules.terrain and modules.physics because render-pipelines.core (URP) depends on both and modules.uielements depends on physics, so they resolve into the build either way. Verified by the tester with a throwaway WebGL smoke build on a plain static server: uGUI, TextMeshPro, sprites, particles, generated audio and UnityWebRequest from StreamingAssets all work, 0 console errors, 0 external requests, and no Pipeline, Newtonsoft or Cecil assemblies in the player.
- 2026-11-19 (phase 0, lead): **Every scripted Editor run exits through `EditorApplication.Exit(code)`; tests run with `-runTests` and no `-quit`.** On this machine, bare `-batchmode -quit` runs crash at shutdown with exit 139 after their work has finished (known issue D1). The cause isn't proven; it is not the Pipeline package or the 0.2 package strip (it still crashes without them). It most likely comes from the Editor's analytics call to the nonexistent host `cdp.cloud.unity3d.com` during teardown. `Exit(code)` and `-runTests` exited 0 on 7 of 7 runs. No settings were changed to get around it. Update (task 0.4): one `Exit(code)` run also crashed after its work was saved (0xC0000005, same Curl error 6 before `Crash!!!`). So a clean exit code is never the evidence: every scripted run writes a results or summary file before exiting, and runs are judged by that file and its timestamp (as ADVISOR 23:20 #1 requires). By the 0.5 fix round, short `Exit` runs (under ~25 s) were crashing almost every time (4 of 4 refusal runs), while longer builds and `-runTests` runs mostly exit 0. Same rule: the file decides.
- 2026-11-19 (phase 0, builder): **Web build uses Gzip with decompression fallback, not Brotli and not uncompressed.** GitHub Pages can't send a Content-Encoding header, so the fallback lets the loader unpack the `.unityweb` files itself; Gzip unpacks faster in JavaScript than Brotli, and its files are a little bigger. Checked with the smoke build on a plain static server that sends no encoding headers: 0 console errors, 12.30 MB download (wasm 7.81 MB, data 4.35 MB). 0.2's defaults with Brotli came to 13.65 MB.
- 2026-11-19 (phase 0, builder): **Build files are named by content hash, Unity's data caching stays on, and the template's `cacheControl` marks `Build/` files immutable and everything else no-store.** A new build gets new file names, so a cached copy can't be stale, and a repeat visit loads the engine from IndexedDB without downloading it again. StreamingAssets (`weeks.json`, `math_config.json`) are requested with no-store, which keeps the weekly word edits visible. `index.html` is fetched by the browser, not the loader, so `cacheControl` can't cover it, and GitHub Pages lets browsers keep it for about 10 minutes. Just after a redeploy, a cached old page could ask for Build files that are gone, so the deploy keeps the previous build's hashed files (task 0.5). Correction after the 0.3 test: the first template regex never matched the loader's relative `Build/...` URLs, so nothing was cached; fixed to `(^|\/)Build\/`, which the tester confirmed in a patched copy (the reload fetched 51 KB instead of 12.3 MB). Also: static and dynamic batching are off for WebGL, because the SRP batcher covers a sprite and UI game.
- 2026-11-19 (phase 0, builder): **Smaller code over build speed: managed stripping High, IL2CPP code generation "optimise size", Wasm code optimisation "Disk Size with LTO", exceptions "Explicitly Thrown Only".** The trade-off is a slower clean build (4 min 22 s for the empty smoke scene) and less forgiving reflection. Explicitly thrown exceptions keep JSON validation errors readable. Code optimisation is stored in `Library/BuildProfiles` (git ignores it), so the build script must set it on every build. The URP asset turns off what a 2D sprite and UI game doesn't use (HDR, shadows, mixed lighting, light cookies, lens flares, LOD cross-fade, terrain holes), unused post-processing variants are stripped, and lightmap and fog variants are stripped in Graphics settings.
- 2026-11-19 (phase 0, builder): **Player identity "hall_pass" / "world tour", Unity splash screen and logo off, project template `WorldTour`, default canvas 1366x768.** The splash adds load time and isn't required. The template is a full-window canvas on the palette pink with a plain loading bar and a lowercase failure message, and it fills the window at 1366x768 and 1920x1080 with no scrollbars or letterboxing.
- 2026-11-19 (phase 0, builder): **`Assets/TextMesh Pro/` (TMP Essential Resources) is kept in the project.** It comes from Unity's own ugui package, not a third-party download, and TextMeshPro needs its settings asset and a default font asset to render any label (task 0.4 onwards). Its LiberationSans font and EmojiOne sprites add about 1.7 MB uncompressed to the data file. Once Caveat Brush and Courier Prime are the default fonts, they can come out.
- 2026-11-19 (phase 0, builder): **`Boot` is the only scene in the build list; the template's `Assets/Scenes/SampleScene.unity` is deleted.** PLAN.md has exactly two scenes (Boot, then Main in phase 2), and an unused template scene would be easy to build by mistake. `ProjectSettings` still has `templateDefaultScene: Assets/Scenes/SampleScene.unity`. That setting only matters when this project is saved as a project template, so I left it alone.
- 2026-11-19 (phase 0, builder): **The Boot title label is empty in the scene file and `Boot.Start` fills it from `WorldTour.Core.GameInfo.Title`, then logs `WT_BOOT_READY` once.** If the text were saved in the scene, a visible title wouldn't prove Core ran. This way the 0.6 browser test's "label visible" moment and the ready line come from the same frame.
- 2026-11-19 (phase 0, builder): **`Assets/Tests/PlayMode/PlayModeAssembly.cs` is an empty internal class with no tests.** Unity skips an assembly definition that has no scripts and logs a warning on every compile. The file keeps the play-mode test assembly compiling with 0 warnings until the first play-mode test lands; delete it then.
- 2026-11-20 (phase 0, builder): **`BuildWeb.Build` builds into a staging folder, then publishes into `tour/`. It keeps one previous build's hashed `Build/` files and never overwrites or deletes anything already in `tour/StreamingAssets/`.** Staging means a failed build never touches the live folder, and `Build/` files go in before `index.html`, so a new page never points at a missing file. GitHub Pages lets browsers cache `index.html` for about 10 minutes, so files named by an older page must survive a deploy; keeping exactly one previous set (recorded in `tour/build.json`, anything older pruned) covers that without letting `tour/` grow. The owner edits `weeks.json` in the deployed folder by hand, so the build only adds missing StreamingAssets files and warns about any that differ. Library-only settings (Web target, "Disk Size with LTO", non-development) are set on every run; ProjectSettings values are logged, never overridden.
- 2026-11-20 (phase 0, lead decision, recorded by builder): **`ProjectSettings.asset` keeps `preloadedAssets: InputSystem_Actions.inputactions`.** Web builds add it because that's how the Input System ships project-wide actions to the player. Keeping the entry and committing it in 0.7 means later builds leave the file byte-identical (checked: same hash before and after a build).
- 2026-11-20 (phase 0, builder): **BuildWeb only writes into folders it can prove it owns (an allowlist, not a denylist).** Inside the repo the only allowed output is `tour/`. Any output folder must be missing, empty, or hold a `build.json` with `"writer": "WorldTour.BuildWeb"` (`-buildForceAdopt` is the only override). Staging must be inside `<project>/Temp`, or outside the repo and missing, empty, or marked with `.buildweb-staging`. The summary may not land in the output or staging folder or elsewhere in the repo. Reason: a denylist missed folders one typo away, `-buildOut ../world_tour` (the owner's finished game, which must never change) and any non-empty staging folder outside the repo (which got deleted). Refusing everything BuildWeb can't prove is its own can't destroy files it doesn't know about.
- 2026-11-20 (phase 1.1, builder): **Core math namespace is `WorldTour.Core.Maths`, not `WorldTour.Core.Math`** (folder stays `Assets/Core/Math/`). A namespace named `Math` under `WorldTour.Core` would hide `System.Math` in every other Core namespace, so each `Math.Floor` there would need `System.` in front.
- 2026-11-20 (phase 1.1, builder): **`Rational` uses `long` with checked arithmetic and throws `OverflowException` where the JS (doubles, exact to 2^53) would silently lose precision; it is always reduced, and `default(Rational)` is 0/1.** Everything a 5th grader sees is far inside both ranges, so results match the JS everywhere they can both be right.
- 2026-11-20 (phase 1.1, builder): **`Rng.Pick` on an empty list consumes one value and then throws (JS returns undefined); `newSeed` is `Rng.NewSeed(Func<double>)` with the random source passed in.** Core stays deterministic, and the sequence after a failed pick still lines up with the JS.
- 2026-11-20 (phase 1.1, builder): **JS cross-check vectors live in `Assets/Tests/EditMode/js_vectors.json`, written by `Tools/js_vectors.mjs` (deterministic: rerunning gives the same bytes).** Doubles are stored as hex bit patterns plus the raw 32-bit value, so the C# check is bit for bit and doesn't depend on any JSON number parser.
- 2026-11-20 (phase 1.2, builder): **Answer, trap and choice values are one `MathValue` struct (number, `{n,d}`, `{x,y}` or null) with double parts, and a part the value doesn't have reads as NaN.** That copies how the JS passes loose values around: `cleanTraps` gets unreduced or invalid fractions, negatives and non-whole numbers and has to drop them the same way, and NaN behaves like JS `undefined` in its comparisons. The answer types are an `AnswerType` enum; `accept.simplest` is a `bool simplest` parameter.
- 2026-11-20 (phase 1.2, builder): **A typed number too big for a 64-bit integer (any whole part above 9,223,372,036,854,775,807, so some 19-digit numbers too, or more than 18 decimal places) reads as bad input ("doesn't read as a number yet") instead of a miss.** The JS turns it into an imprecise double and calls it wrong. Nothing a child would type is near that size.
- 2026-11-20 (phase 1.2, builder): **`show()` formats whole numbers with the invariant culture's "#,##0.###".** It uses the same separators as `toLocaleString('en-US')`, and unlike an "en-US" CultureInfo it exists in a Web player built without culture data. A test checks the output under de-DE, fr-FR, hi-IN and ar-SA.
- 2026-11-20 (phase 1.2, builder): **`math_config.json` keeps the JS export names as its keys (`ENABLED_SKILLS`, `BOUNDS`), and so does the `MathConfig` model.** A missing skill switch stays on, as the JS treats a missing key as shown. A missing bound stays -1, and `Validate()` reports it. JsonUtility was checked to keep field initializers for missing keys.
- 2026-11-20 (phase 1.2, builder): **The answer and mistake vectors go in a second file, `answer_vectors.json`, written by `Tools/answer_vectors.mjs`.** That leaves 1.1's `js_vectors.json` byte-identical. Both are plain ASCII, with `\uXXXX` escapes.
- 2026-11-20 (phase 1.3a, builder): **`Problem` (Core/Math/Gen) has typed fields for the keys every generator shares (skill, level, kind, seed, prompt, label, answer, `Simplest` for accept.simplest, choices, traps, steps, builder) and `JsonValue` trees for `params` and `work`, built in the same shape as the JS object literals.** Those two differ per skill, so a tree lets 1.3b add generators without changing the type. A C# null `Work` or `Builder` means the JS object has no such key; `JsonValue.Null` means the key is there and null.
- 2026-11-20 (phase 1.3a, builder): **Generator vectors are hashes, not full problems: `problem_vectors.json` (158 KB, written by `Tools/gen_vectors.mjs`) holds the sha256 of each problem's canonical JSON for 200 seeds per skill and level, one digest over all 3,000 `seeds(level)` problems per skill and level, and 23 full problems for diffing.** Full JSON for 1,800 problems would be about 4 MB. Canonical JSON = sorted keys, no whitespace, JS `String(n)` numbers, non-ASCII escaped as lowercase `\u00xx`; `Problem.ToCanonicalJson` writes the same bytes.
- 2026-11-20 (phase 1.3a, builder): **`guard.js` (`leaks` and `guarded`) was ported in 1.3a, as `Gen/Guard.cs`, not left for 1.3b.** dec, md and frac all call `guarded(build)`, and 56 of the 27,000 volume-set problems are re-rolls (up to 3 builds), so the problems can't match the JS without it.
- 2026-11-20 (phase 1.3a, builder): **The "nothing negative shown" scan reads prompt, label, steps, the answer and choices as text; trap values are checked only as values (non-negative), not against the grade bounds.** The web game never displays a trap: it matches the child's typed answer against it and shows a canned line for `trap.why` (`modes/math/parts.js`). So an added-denominators trap like 13/15 is fine. Grade bounds come from `Assets/StreamingAssets/math_config.json`.
- 2026-11-20 (phase 1.3b, builder): **A choice whose JS value is a string (the tour budget's expressions) is a `Choice` with `Text` set and `Value = MathValue.Null`; every other choice keeps `Text = null`, so `Choice.Value` and the 1.2 constructor work as before.** `Choice.IsText` tells them apart, `Problem.ToJson` writes the text as a JSON string, and the contract keys a text choice by its text, as the JS `key()` does with `String(v)`.
- 2026-11-20 (phase 1.3b, builder): **The 1.3b vectors were appended to `problem_vectors.json` (now 362 KB, still version 1): xy, vol, ops and flu groups and samples come after the 1.3a ones, which are unchanged entry for entry.** `gen_vectors.mjs` lists the skills in index.js order with the 1.3a three first, and gained `--out <file>`.
- 2026-11-20 (phase 1.3b, builder): **The generator tests use, for each grade bound, the stricter of the JS constant (pinned in the test: 10000, 12, 10, 1000) and `math_config.json`; money in the text must be under `moneyCents` (`<`, as the JS "money under $100").** The generators don't read BOUNDS, so a looser deployed config must not loosen the test (tester note).
- 2026-11-20 (phase 1.3b, builder): **The shown-text scan also reads trap values for flu and ops (their distractors are displayed: soundcheck.js, budget.js; flu builds its traps from its choices), but leaves out xy `params.dx`/`dy`.** Those are signed moves; the player only reads them as "3 left" (checked against the prompt), and stage.js never displays them.
- 2026-11-20 (phase 1.3b, builder): **The ops and flu checks evaluate expressions with `ExprEval`, a small evaluator in the test assembly that shares nothing with `OrderOps`, in place of the JS test's `Function('return (' + expr + ')')`.**
- 2026-11-20 (phase 1.4, builder): **The show engine's namespace is `WorldTour.Core.Shows` (folder `Assets/Core/Show/`).** Same reason as `Maths`: a namespace called `Show` could hide a `Show(...)` member elsewhere in Core.
- 2026-11-20 (phase 1.4, builder): **Everything random in a show (pickWords, pickProblems' newSeed, the encore shuffle) takes a `Func<double>` that stands in for JS `Math.random`; pass `new Rng(seed).Next` in tests.** With the same sequence, the picks match the JS exactly (checked against the JS functions). UI-only randomness (dog lines, cheers, the ladder's name coin flip) stays in the Game layer.
- 2026-11-20 (phase 1.4, builder): **The engine refuses misuse the JS leaves to the modes: answering a song twice, answering after Reveal, or acting before Start or after the end throws `InvalidOperationException`, and negative soundcheck bonus fans throw.** A Game bug then shows up at once and can never change fans.
- 2026-11-20 (phase 1.4, builder): **A hint never subtracts fans (the JS never does); the `HintUsed` event reports its cost as how much it lowered this song's reward (for example 3000 down to 500), which is 0 for a second hint.** So "hints cost fans" is visible to the Game layer without anything earned being taken away.
- 2026-11-20 (phase 1.4, builder): **The engine updates the `SkillRecord` it is given in place and reports everything else that progress must save as events (`FansAwarded`, `ItemRecorded` with clean/missed/keep/hinted, `SkillRecorded`, `LevelChanged`, `MistakeNoted`).** Venue unlocks (JS `P.addFans` return value) are left to 1.5/1.6, which react to `FansAwarded`.
- 2026-11-20 (phase 1.4, builder): **`WordItem` holds `W`, `S` and an opaque `Data` object for the week's word record until 1.7 adds the Word model; the math generator is injected as `Func<int, long, Problem>` (default `Generators.Generate(skill, level, seed)`).**
- 2026-11-20 (phase 1.4, builder): **`LevelRules.Record` adds a missing `byLevel` row (a hand-edited save) instead of failing as the JS would.**
- 2026-11-20 (phase 1.7, builder): **weeks.json is `{ "weeks": [ ... ] }`, not a bare array.** A wrapper object is what JsonUtility would need, and it leaves room for a later field. The converter keeps weeks.js's order (newest first) and field order (w, s, h, x, prefix), with a 2-space indent and the same bytes on every run. It refuses to replace an existing file that differs unless given `--force`, so hand edits can't be lost by rerunning it.
- 2026-11-20 (phase 1.7, builder): **The data loader fills the models straight from the strict JSON tree; JsonUtility is not used for weeks.json or math_config.json.** The tree already holds every key and type (needed for the raw checks), and direct field assignment uses no reflection, so High stripping has nothing to remove. JsonUtility would also turn an absent `x` into "" and an absent `prefix` into an empty object (Unity serializes nested classes inline). The models stay [Serializable] with public fields.
- 2026-11-20 (phase 1.7, builder): **StrictJson returns the shared `JsonValue` tree (coordinator's interface for 1.5) and throws `StrictJsonException : FormatException` with Line, Column and Reason.** JsonValue gained additive members only: Line, Column, RawNumber, IsWholeNumberToken, TryGetKeyPosition, plus internal NewNull and AddParsed. The canonical writer is unchanged; the 1.3 vector tests (92 ProblemVectorTests) still pass.
- 2026-11-20 (phase 1.7, builder): **Loading takes three steps: strict parse, then raw keys and types, then Validate() (meaning), done week by week; a week's meaning checks run only if its raw checks passed.** One mistake gives one message. A config with any error falls back to `MathConfig.WebDefaults()`. (Weeks: see the skipping line below; that replaces the first draft, which refused the whole file on any error.)
- 2026-11-20 (phase 1.7, builder): **Errors and warnings.** Errors: missing or empty w, s, h, id or label; a bad or unreal date; a duplicate week id; a duplicate word in a week; a word that isn't trimmed lowercase (parts.js:43: a typed answer could never match it); an x without exactly one ___; a missing prefix part; p + root not spelling w. Warnings (the game still loads): syllables don't spell the word; a clue or sentence gives the word away; and 1 to 3 words (not 0) having x or a prefix, which hides that mode. A week with none is taken as intended, unlike content_review.mjs, which flags 0 too.
- 2026-11-20 (phase 1.7, builder): **C#/Node parity is checked by a test, not kept in a shared rule table.** Several rules are code, not data. `validate_data.mjs` mirrors the C# parser and rules line for line. `--parity` writes `Tests/EditMode/DataSamples/expected_findings.json` (63 sample files), and DataFilesTests asserts the C# findings match it exactly (severity, line, column, message). `--parity-check` tells you when the file is stale.
- 2026-11-20 (phase 1.7, builder): **validate_data.mjs exits 1 on errors and 0 when there are only warnings (it lists them and ends "ok to load").** With no arguments it checks each file in tour/StreamingAssets/, falling back to the project copy file by file.
- 2026-11-20 (phase 1.7, builder): **DataLoader adds `?v=<ticks>` to http(s) StreamingAssets requests**, because the template's no-store rule covers Unity's own data loader, not UnityWebRequest. Over file:// (the Editor) it adds no query.
- 2026-11-20 (phase 1.7, lead): **A weeks.json with a broken week still plays the valid weeks.** The file is refused only if it can't be parsed at all (syntax error), or if no week is valid. Otherwise the broken weeks are skipped and a plain message lists them for a grown-up. Reason: a typo in a new week on a Sunday night shouldn't leave her with no words on Monday. The terminal validator still catches it before a push. Also accepted: weeks with 0 sentences or 0 prefixes get no mode-threshold warning (deliberate weeks; only 1–3 warns).
- 2026-11-20 (phase 1.7, builder, per coordinator 02:30): **A broken week is skipped and the other weeks load.** weeks.json is refused (`WeeksLoad.File` null) only when it can't be parsed, has no `weeks` list, or no week is valid. Each skipped week keeps its own error findings, and one closing plain line lists them all: "the game skips week 2026-11-16 (line 58) until it is fixed; the other weeks load". `WeeksLoad.Skipped` holds the same names. The line number tells two weeks with the same id apart. An unknown top-level key is an error but skips nothing. validate_data.mjs still exits 1, since a skipped week is an error to fix before pushing.
- 2026-11-20 (phase 1.7, builder): **When two weeks share an id, the copy higher in the file is kept and the later one is skipped.** The owner adds new weeks at the top, and the web game opens a week by id with `WEEKS.find` (show.js:13), which takes the first match. The check is against weeks already kept, so if the top copy is itself broken and skipped, the next copy with that id loads.
- 2026-11-20 (phase 1.5, builder): **The save is read and written by hand through `JsonValue` and builder 3's `StrictJson`, with no JsonUtility and no reflection, so High stripping in the web player can't remove anything it needs.** The stored text keeps insertion key order (the order JSON.stringify gives, which the office tie-breaks need) and escapes non-ASCII as \uXXXX, so it equals the web game's stored text for the same state; canonical sorted JSON is used only for comparisons (corrected by the lead after the 1.5 tester).
- 2026-11-20 (phase 1.5, builder): **`SaveJson.Migrate` follows store.js `migrate` key by key, with three deliberate differences.** (1) Keys the save doesn't model are dropped (the JS keeps them). (2) A value of the wrong type keeps the default, where the JS would keep it and then misbehave: `"500"` fans would concatenate, an `unlocked` string would spread into letters, an `unlocked` object would throw. Non-strings in string lists are dropped, and fractional numbers are floored. (3) A partial skill record is filled in, and a review entry without a string skill and numeric level and seed is dropped. Every JS-made save in `save_vectors.json` migrates byte for byte.
- 2026-11-20 (phase 1.5, builder): **Review problems are stored as the generator's own JSON (a `JsonValue`) and read back by `ProblemJson`; one that passes the JS `usable()` test but can't be read as a problem is treated like an old seed-only entry (regenerated).** All 7 skills x 3 levels x 60 seeds come back identical through the save.
- 2026-11-20 (phase 1.5, builder): **The export code is `WT1-` + base64url(raw DEFLATE of the save JSON) + `-` + CRC-32 (8 hex digits), and the export file is the save JSON itself. The DEFLATE is plain C# in Core (`Deflate.cs`), not System.IO.Compression, because the web player's native zlib isn't guaranteed.** Any zlib reads and writes the same stream; this is tested against DeflateStream both ways. Whitespace in a pasted code is ignored.
- 2026-11-20 (phase 1.5, builder): **Import replaces the whole save; there is no merge, and it happens only through `ExportCode.Apply` after the UI has shown `Preview` and the player has confirmed.** Preview lists, in plain lines, anything that would be lost (fans, venues, stickers, items, show history). A bad code changes nothing and gets a short lowercase message.
- 2026-11-20 (phase 1.5, builder): **`ProgressRules.AddFans` throws on a negative amount; spending (task 1.6) changes only the balance.** Lifetime fans and unlocked venues only ever go up.
- 2026-11-20 (phase 1.5, builder): **The venue table is `Core/Data/Venues.cs` (from data/venues.js), so 1.6 can reuse it.** The curly quote in one blurb is built from its character code, so the source stays ASCII.
- 2026-11-20 (phase 1.5, builder): **Day stamps: `Dates.DaysBetween` reads only "yyyy-mm-dd" (what the game writes) and returns null where the JS gives NaN; "today" is always passed in by the Game layer.**
- 2026-11-20 (phase 1.5, builder): **The Editor and desktop save is one file per key under `Application.persistentDataPath` (written to a temp file, then moved), not PlayerPrefs; the web save is localStorage through `Plugins/WebGL/storage.jslib`, with an in-memory fallback.**
- 2026-11-20 (phase 1.5, builder; approved by lead 02:58: "nothing earned is ever taken away" outranks the one-key FYI): **If the stored save can't be read, `SaveStore` copies the text once to a second key, `worldtour.v1.unreadable`, before the first new save overwrites it.** The JS silently starts over and loses everything at its next save. This is the only case with a second key, which bends the advisor's "one key" FYI (22:35).
- 2026-11-20 (phase 1.6, builder): **The meta layer is `Core/Meta/` (namespace `WorldTour.Core.Meta`): `Shop` and `Milestones` hold shop.js and milestones.js, `MetaRules` holds the backstage and journal functions of meta.js, `Office` holds `MISTAKES`, `office()` and `mins()`.** It works directly on 1.5's `SaveBlob` types instead of a second save model; the members it reads are listed in the 1.6 hand-back.
- 2026-11-20 (phase 1.6, builder): **A milestone's rule is `Func<SaveBlob, IReadOnlyList<ModeInfo>, bool>`, and `ModeInfo` (id, name, kind, skill) is the part of a modes/index.js entry that meta.js reads.** The Game layer builds the mode list, as progress.js `setModes` does in the web game.
- 2026-11-20 (phase 1.6, builder): **`buy` returns a `BuyResult` struct with a `BuyReason` enum (None, Unknown, Owned, Short) and `Need`, in place of the JS `{ ok, reason, need }` object.**
- 2026-11-20 (phase 1.6, builder): **The office breaks ties between words or mistake labels with ordinal comparison, where the JS uses `localeCompare`.** All 22 words are lowercase a-z and no two labels differ first at a punctuation or non-ASCII character, so the order is the same; ordinal also doesn't depend on culture data the Web player may not have.
- 2026-11-20 (phase 1.6, builder): **`office()` reads only a "yyyy-mm-dd" day for today and throws `ArgumentException` for anything else (the JS throws a RangeError at toISOString).** With `days` 0 or less, nothing is parsed, as in the JS.
