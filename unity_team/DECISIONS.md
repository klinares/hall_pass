# Decisions

Small, reversible choices made by the team, one line each with the reason. Anything bigger goes in `QUESTIONS.md`.

- 2026-11-19 (phase 0, lead): **UI system is uGUI with TextMeshPro; UI Toolkit is not used.** The scrapbook look needs rotated sprite stickers, hard offset shadows, per-element squash-and-spring tweens, and particles and world-space sprites (dog, crowd) layered with the UI. Those are ordinary RectTransform, Image and Canvas sorting work in uGUI and fight UI Toolkit. uGUI is already in the project, so no package is added.
- 2026-11-19 (phase 0, lead): **Editor is 6000.3.29f1** (the project's own version, at D:\Unity\Editors). The newer 6000.6.10f1 also installed on this machine is not used, and the project is not upgraded.
- 2026-11-19 (phase 0, builder): **Packages stripped for a small web download; Pipeline added.** Added `com.unity.pipeline` 1.0.0 (registry latest, min Unity 6000.0; pulls nuget.mono-cecil and nuget.newtonsoft-json) for Editor control. Removed packages visualscripting, multiplayer.center, collab-proxy, 2d.aseprite, 2d.psdimporter and modules cloth, terrainphysics, vehicles, vr, xr, wind, ai, umbra, androidjni, unityanalytics, video. Kept modules.terrain and modules.physics because render-pipelines.core (URP) depends on both and modules.uielements depends on physics, so they resolve into the build either way. Verified by the tester with a throwaway WebGL smoke build on a plain static server: uGUI, TextMeshPro, sprites, particles, generated audio and UnityWebRequest from StreamingAssets all work, 0 console errors, 0 external requests, and no Pipeline, Newtonsoft or Cecil assemblies in the player.
- 2026-11-19 (phase 0, lead): **Every scripted Editor run exits through `EditorApplication.Exit(code)`; tests run with `-runTests` and no `-quit`.** On this machine, bare `-batchmode -quit` runs crash at shutdown with exit 139 after their work has finished (known issue D1). The cause isn't proven; it is not the Pipeline package or the 0.2 package strip (it still crashes without them). It most likely comes from the Editor's analytics call to the nonexistent host `cdp.cloud.unity3d.com` during teardown. `Exit(code)` and `-runTests` exited 0 on 7 of 7 runs. No settings were changed to get around it. Update (task 0.4): one `Exit(code)` run also crashed after its work was saved (0xC0000005, same Curl error 6 before `Crash!!!`). So a clean exit code is never the evidence: every scripted run writes a results or summary file before exiting, and runs are judged by that file and its timestamp (as ADVISOR 23:20 #1 requires). By the 0.5 fix round, short `Exit` runs (under ~25 s) were crashing almost every time (4 of 4 refusal runs), while longer builds and `-runTests` runs mostly exit 0. Same rule: the file decides.
- 2026-11-19 (phase 0, builder): **Web build uses Gzip with decompression fallback, not Brotli and not uncompressed.** GitHub Pages can't send a Content-Encoding header, so the fallback lets the loader unpack the `.unityweb` files itself; Gzip unpacks faster in JavaScript than Brotli, and its files are a little bigger. Checked with the smoke build on a plain static server that sends no encoding headers: 0 console errors, 12.30 MB download (wasm 7.81 MB, data 4.35 MB). 0.2's defaults with Brotli came to 13.65 MB.
- 2026-11-19 (phase 0, builder): **Build files are named by content hash, Unity's data caching stays on, and the template's `cacheControl` marks `Build/` files immutable and everything else no-store.** A new build gets new file names, so a cached copy can't be stale, and a repeat visit loads the engine from IndexedDB without downloading it again. StreamingAssets (`weeks.json`, `math_config.json`) are requested with no-store, which keeps the weekly word edits visible. `index.html` is fetched by the browser, not the loader, so `cacheControl` can't cover it, and GitHub Pages lets browsers keep it for about 10 minutes. Just after a redeploy, a cached old page could ask for Build files that are gone, so the deploy keeps the previous build's hashed files (task 0.5). Correction after the 0.3 test: the first template regex never matched the loader's relative `Build/...` URLs, so nothing was cached; fixed to `(^|\/)Build\/`, which the tester confirmed in a patched copy (the reload fetched 51 KB instead of 12.3 MB). Also: static and dynamic batching are off for WebGL, because the SRP batcher covers a sprite and UI game.
- 2026-11-19 (phase 0, builder): **Smaller code over build speed: managed stripping High, IL2CPP code generation "optimise size", Wasm code optimisation "Disk Size with LTO", exceptions "Explicitly Thrown Only".** The trade-off is a slower clean build (4 min 22 s for the empty smoke scene) and less forgiving reflection. Explicitly thrown exceptions keep JSON validation errors readable. Code optimisation is stored in `Library/BuildProfiles` (git ignores it), so the build script must set it on every build. The URP asset turns off what a 2D sprite and UI game doesn't use (HDR, shadows, mixed lighting, light cookies, lens flares, LOD cross-fade, terrain holes), unused post-processing variants are stripped, and lightmap and fog variants are stripped in Graphics settings.
- 2026-11-19 (phase 0, builder): **Player identity "hall_pass" / "world tour", Unity splash screen and logo off, project template `WorldTour`, default canvas 1366x768.** The splash adds load time and isn't required. The template is a full-window canvas on the palette pink with a plain loading bar and a lowercase failure message, and it fills the window at 1366x768 and 1920x1080 with no scrollbars or letterboxing.
- 2026-11-19 (phase 0, builder): **`Assets/TextMesh Pro/` (TMP Essential Resources) is kept in the project.** It comes from Unity's own ugui package, not a third-party download, and TextMeshPro needs its settings asset and a default font asset to render any label (task 0.4 onwards). Its LiberationSans font and EmojiOne sprites add about 1.7 MB uncompressed to the data file. Once Caveat Brush and Courier Prime are the default fonts, they can come out.
- 2026-11-19 (phase 0, builder): **`Boot` is the only scene in the build list; the template's `Assets/Scenes/SampleScene.unity` is deleted.** PLAN.md has exactly two scenes (Boot, then Main in phase 2), and an unused template scene would be easy to build by mistake. `ProjectSettings` still has `templateDefaultScene: Assets/Scenes/SampleScene.unity`. That setting only matters when this project is saved as a project template, so I left it alone.
- 2026-11-19 (phase 0, builder): **The Boot title label is empty in the scene file and `Boot.Start` fills it from `WorldTour.Core.GameInfo.Title`, then logs `WT_BOOT_READY` once.** If the text were saved in the scene, a visible title wouldn't prove Core ran. This way the 0.6 browser test's "label visible" moment and the ready line come from the same frame.
- 2026-11-19 (phase 0, builder): **`Assets/Tests/PlayMode/PlayModeAssembly.cs` is an empty internal class with no tests.** Unity skips an assembly definition that has no scripts and logs a warning on every compile. The file keeps the play-mode test assembly compiling with 0 warnings until the first play-mode test lands; delete it then.
- 2026-11-20 (phase 0, builder): **`BuildWeb.Build` builds into a staging folder, then publishes into `tour/`. It keeps one previous build's hashed `Build/` files and never overwrites or deletes anything already in `tour/StreamingAssets/`.** Staging means a failed build never touches the live folder, and `Build/` files go in before `index.html`, so a new page never points at a missing file. GitHub Pages lets browsers cache `index.html` for about 10 minutes, so files named by an older page must survive a deploy; keeping exactly one previous set (recorded in `tour/build.json`, anything older pruned) covers that without letting `tour/` grow. The owner edits `weeks.json` in the deployed folder by hand, so the build only adds missing StreamingAssets files and warns about any that differ. Library-only settings (Web target, "Disk Size with LTO", non-development) are set on every run; ProjectSettings values are logged, never overridden.
- 2026-11-20 (phase 0, lead decision, recorded by builder): **`ProjectSettings.asset` keeps `preloadedAssets: InputSystem_Actions.inputactions`.** Web builds add it because that's how the Input System ships project-wide actions to the player. Keeping the entry and committing it in 0.7 means later builds leave the file byte-identical (checked: same hash before and after a build).
- 2026-11-20 (phase 0, builder): **BuildWeb only writes into folders it can prove it owns (an allowlist, not a denylist).** Inside the repo the only allowed output is `tour/`. Any output folder must be missing, empty, or hold a `build.json` with `"writer": "WorldTour.BuildWeb"` (`-buildForceAdopt` is the only override). Staging must be inside `<project>/Temp`, or outside the repo and missing, empty, or marked with `.buildweb-staging`. The summary may not land in the output or staging folder or elsewhere in the repo. Reason: a denylist missed folders one typo away, `-buildOut ../world_tour` (the owner's finished game, which must never change) and any non-empty staging folder outside the repo (which got deleted). Refusing everything BuildWeb can't prove is its own can't destroy files it doesn't know about.
